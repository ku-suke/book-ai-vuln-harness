# 第8章：判定エンジン（オラクル）と開発者向けレポート

テスト用のリクエストを送信したあと、ハーネス側には最も重要な仕事が待っています。

それは**「本当に意図しない挙動（認可の抜け穴など）が再現したのかを、どうやって機械的に判定するか」**です。

ソフトウェアテストの世界では、テストの実行結果が正しいかどうかを判定する仕組みのことを「テストオラクル（Test Oracle）」と呼びます。自律型のセキュリティ診断において、このオラクルをどう設計するかは、ツールの実用性を左右する極めて大きなポイントです。

本章では、一般的なHTTPレスポンスのチェックだけでは見抜けないケースを整理し、ホワイトボックス環境だからこそできる「テストDBの直接参照による判定」、そして開発者が迷わず修正できる「再現コード付きレポートの自動生成」について見ていきましょう。

---

## 8.1 機械的判定エンジン（オラクル）の設計

### HTTPレスポンスだけを見ていると騙される

ブラックボックス診断のツールが誤検知（あるいは見落とし）を多発させる大きな原因は、「HTTPのステータスコードや画面の見た目だけで成否を判定しているから」です。

現実のWebアプリケーションでは、次のような「見かけと実態のズレ」が日常茶飯事のように起こります。

1. **画面上はエラーなのに、裏では処理が通っていたケース:**  
   たとえば画面のリダイレクト処理で例外が起き、レスポンスとしては `500 Internal Server Error` が返ってきたとします。外側から見ると「失敗した」ように見えますが、実はDBへの書き込み処理は例外の手前で完了していて、データが不正に更新されていた……というパターンです。
2. **ステータス200なのに、実は何も起きていなかったケース:**  
   APIがどんなリクエストに対しても `200 OK` を返し、レスポンスのJSONの中に `{"success": false, "message": "Permission denied"}` と書いてあるような設計です。ステータスコードだけを見ているツールは「成功した！」と勘違いして誤検知（False Positive）を出してしまいます。

```text
HTTPレスポンスだけの判定（危うい）:
  リクエスト送信 ──> [ステータスコード 200] ──> 「通った？」(誤判定の元)
  リクエスト送信 ──> [ステータスコード 500] ──> 「弾かれた？」(実はDB更新済みかも)

ホワイトボックスの判定（確実）:
  リクエスト送信 ──> 【テストDBを直接SQLで確認】
                      ├─ 他人のデータが書き換わっているか？
                      └─ 意図しないレコードが増えているか？
```

### ホワイトボックス特権：テストDBを直接クエリして確認する

ここで守る側だけの強みである「データベースへの直接アクセス」を活かします。

リクエストを送った直後に、ハーネス側からテストDBに対して検証用のSQLクエリを発行するのです。

#### BOLA（認可不備）の判定クエリ例
第7章で見た「ユーザーBが、ユーザーAの所有するプロジェクト（ID: 101）の名前を書き換えるリクエスト」を例に考えてみます。

リクエストを送信したあと、エージェント（またはハーネスの判定ロジック）はテストDBに直接問い合わせを行います。

```sql
-- プロジェクト101の現在のレコードを取得して確認する
SELECT id, name, updated_at 
FROM projects 
WHERE id = 101;
```

もし、このクエリの結果として取得した `name` が、リクエストで送りつけたダミー文字列（`HACKED_BY_USER_B` など）に書き換わっていれば、レスポンスのステータスコードが200だろうが500だろうが関係なく、**「認可チェックをすり抜けてデータが書き換わってしまった」という事実が確定**します。

#### 副作用のない参照系（情報漏洩）の判定
更新系ではなく「他人の機密データを閲覧できるか」という参照系のテストであれば、あらかじめDBから「ユーザーAの機密データ（例: APIキーや個人情報）」を取得しておき、ユーザーBのトークンで叩いたレスポンスボディの中にその機密文字列が含まれているかどうかを文字列一致で判定します。

DBの内部状態を基準に合否を判定することで、フレームワークのエラーハンドリングに惑わされることなく、確実な実証（No exploit, no report）が達成できるわけです。

## 8.2 開発者がすぐ直せる再現レポートの自動生成

問題が確実に再現したと分かったら、最後の仕上げは「開発チームへのレポート作成」です。

セキュリティのレポートというと、何十ページもある仰々しいPDFを思い浮かべるかもしれませんが、開発者が本当に求めているのはそんなものではありません。現場の開発者が見たいのは、**「自分のコードの何行目が悪くて、どう叩けば手元で1発で再現するのか」**というシンプルな情報です。

`auditkit` では、エージェントに以下のようなMarkdown形式のレポートを自動生成させます。

### 自動生成されるレポートのフォーマット例

```markdown
# [脆弱性検出] プロジェクト更新APIにおける認可チェック漏れ (BOLA / IDOR)

## 概要
ユーザーAが所有するプロジェクトに対して、無関係な一般ユーザーBの認証トークンを用いた更新リクエストが成功することを確認しました。

* **重要度:** High
* **該当エンドポイント:** `PATCH /api/projects/{id}`
* **該当ソースコード:** `app/Http/Controllers/ProjectController.php` (L42-L55)

---

## 原因となっているコード
`ProjectController.php` の 45行目付近において、リクエスト送信者が対象プロジェクトの所有者であるかどうかの認可チェックが行われていません。

```php
// app/Http/Controllers/ProjectController.php:42
public function update(Request $request, $id)
{
    $project = Project::find($id); // <-- ここで所有者チェックがない
    $project->update($request->only(['name', 'description']));
    return response()->json($project);
}
```

---

## ローカルでの再現手順 (PoC)
テスト環境を起動した状態で、以下のコマンドを実行すると再現します。

```bash
# ユーザーBのトークンで、ユーザーAのプロジェクト (ID: 101) を更新する
curl -i -X PATCH http://localhost:8080/api/projects/101 \
  -H "Authorization: Bearer <USER_B_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"name": "UNAUTHORIZED_UPDATE_TEST"}'
```

### 実行結果
* **HTTPステータス:** `200 OK`
* **DB確認:** `SELECT name FROM projects WHERE id = 101;` の値が `UNAUTHORIZED_UPDATE_TEST` に更新されることを確認済み。

---

## 推奨される修正方法
LaravelのPolicy（認可機能）または `authorize` メソッドを呼び出し、実行ユーザーがプロジェクトの管理者であることを確認してください。

```php
public function update(Request $request, $id)
{
    $project = Project::findOrFail($id);
    $this->authorize('update', $project); // 所有者チェックを追加
    $project->update($request->only(['name', 'description']));
    return response()->json($project);
}
```
```

### このレポートが喜ばれる理由

1. **修正すべきファイルの行数が明記されている:** どこを直せばいいか一瞬で分かります。
2. **コピペで動く再現コマンド（curl）が付いている:** 開発者が修正したあと、手元で同じcurlを叩くだけで「ちゃんと直ったか（403が返るようになったか）」を即座に確認できます。
3. **具体的な修正コードの提案がある:** 単にダメ出しをするだけでなく、「こう直すと良いですよ」というコードスニペットまで添えてあげることで、修正までの心理的ハードルを大きく下げることができます。

## まとめ

本章では、判定の精度を高める「オラクル」と「レポート生成」について解説しました。

* **HTTPレスポンスだけに頼らない:** 画面のエラーやステータスコードの偽装に惑わされない設計にする
* **テストDBを直接クエリする:** DBの値が実際に書き換わったかを直接確認することで、誤検知をゼロにする
* **開発者ファーストなレポート:** 該当コードの行数、手元で叩ける最小限のcurl、修正提案コードを添えてあげる

これで、脆弱性を検証してレポートを返すハーネスのコア機能が一通り完成しました。
