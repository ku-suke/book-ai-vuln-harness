# 第1章：AI攻撃エージェント時代における「守り側」の戦略

Webアプリケーションセキュリティを取り巻くゲームのルールは、ここ数年で根底から覆りつつあります。

これまで「攻撃」と「防御」の間には、ある種の非対称性が存在していました。「攻撃者はたった1つの穴を見つければよく、防御者はすべての穴を塞がなければならない」という防御側不利の構図です。しかし、かつてはその攻撃を実行するために、高度な技術を持つ人間のペンテスターや攻撃者が、膨大な時間と労力をかけて偵察（Reconnaissance）や脆弱性の実証を行っていました。攻撃者側にも「人的リソース」という明確な物理的制約が存在していたのです。

いま、その制約が崩壊しようとしています。安価な大規模言語モデル（LLM）と自律エージェント基盤の台頭により、偵察からエクスプロイトの試行、PoC（Proof of Concept）コードの組み立てに至るプロセスが、24時間365日休むことなく自律実行される時代が到来しました。

本章では、攻撃エージェントの現実を直視しつつ、なぜ従来のブラックボックス型スキャナでは太刀打ちできないのか、そして**守る側だけが持つ圧倒的な特権「ホワイトボックス」**を活かしてどう戦うべきなのか、その戦略的土台を整理します。

---

## 1.1 脅威の現状と自動化された攻撃

### ARTEX侵害事例が突きつけた現実

近年観測された脅威アクター「ARTEX」をはじめとする攻撃キャンペーンは、セキュリティ業界に強烈なインパクトを与えました。彼らが用いた手法の本質は、超高度な未知のゼロデイ攻撃ではありません。**「安価なLLM APIと自律型エージェントツールを組み合わせた、総当たり的な侵入実証の自動化」**です。

従来のボットネットや自動攻撃スクリプトは、正規表現ベースの既知パターンをランダムなIPアドレスへ投げつける単純なものでした。WAF（Web Application Firewall）のシグネチャで容易に弾かれ、少しパラメータ構造が変わるだけで無力化されていたのです。

しかし、自律エージェントを用いた攻撃は全く異なります。

```text
従来のスクリプト攻撃:
[固定のPayload送信] ──> [403/エラー] ──> [諦める / 次のIPへ]

自律型AIエージェントによる攻撃:
[画面・APIを自律探索] 
   └──> [レスポンスの文脈をLLMが読解]
           └──> [WAFの拒否理由やエラーメッセージを分析]
                   └──> [Payloadを変異・再適応させて再試行]
                           └──> [侵害成功まで自律ループ]
```

エージェントはHTTPレスポンスの文脈を理解し、「なぜリクエストが弾かれたのか」「入力フォームのバリデーション仕様はどうなっているのか」を自律的に推論します。そして、エラーメッセージや挙動の差異を手がかりに、Payloadを動的に変異させながら突破口を探し続けます。

オープンソースの世界でも、Kali Linuxの多彩なツール群をLLMが操るペンテストエージェント（Strixなど）が登場し、その攻撃能力と適応力は急速に実証されつつあります。これが意味するのは、**「中堅・中小のWebサービスや社内システムであっても、熟練ハッカーがつきっきりで侵入テストを仕掛けてくるのと同等の脅威に、日常的に晒される」**ということです。

攻撃の限界費用（マージナルコスト）がほぼゼロになった世界において、人間の手動レビューや年1回の第三者ペンテストだけで守り切ることは、構造的に不可能です。

## 1.2 既存ブラックボックススキャナの限界

「攻撃者が自動化ツールを使ってくるなら、こちらも自動スキャナを回せばいいのではないか？」

そう考えるのは自然です。事実、世の中には多くのDAST（Dynamic Application Security Testing）ツールや脆弱性スキャナ（OWASP ZAP、Burp Suite、市販の診断SaaS）が存在します。しかし、自社プロダクトの開発・運用現場でこれらのツールを本格的にCI/CDへ組み込もうとしたエンジニアは、ほぼ例外なく次の壁にぶつかります。

### 1. 誤検知（False Positive）の山と「開発者の疲弊」
ブラックボックススキャナは、対象アプリケーションの内部実装を知りません。単にステータスコードが `500 Internal Server Error` になった、あるいはレスポンスの中に特定の文字列が含まれていた、という表面的な挙動だけで「SQLインジェクションの可能性あり」といったアラートを大量に吐き出します。

結果として、開発チームの手元には数十〜数百件の「怪しいレポート」が届きます。その大半を人間が1件ずつトリアージし、「フレームワークの型変換エラーで落ちただけで、SQLiは成立していない」と判定する作業に追われます。この狼少年効果により、現場は次第にアラートを無視するようになります。

### 2. 「コンテキスト（文脈）」と「認可」の壁
近年のWebアプリケーションにおける脆弱性の主戦場は、単純な反射型XSSや単純なSQLインジェクションから、**BOLA（Broken Object Level Authorization / IDOR）やビジネスロジックの不備**へと移行しています。

* 「ユーザーAでログインし、組織を作成し、招待状を発行したうえで、ユーザーBのトークンを使ってその招待を不正承諾できるか？」
* 「ショッピングカートでクーポン適用APIを叩いた直後に、別ウィンドウから数量変更APIを割り込ませて決済金額を改ざんできるか？」

こうした脆弱性は、複数画面にまたがる状態遷移、ロール（権限）、認可境界といった深いビジネス文脈を理解していなければ絶対に発見できません。外部からクロールして画面を叩くだけのブラックボックスツールには、そもそも「何が正常で、何が異常（認可違反）なのか」を判定する術がないのです。

### 3. LLMを無秩序に野に放つ危険性（暴走とコスト）
「では、LLMエージェントにブラウザを渡して、ブラックボックスで勝手に探索させればいいのでは？」というアプローチも試みられています。しかし、適切な制約とコンテキストを持たない自律エージェントは、次のような致命的な問題を引き起こします。

* **無限推論ループとトークン浪費:** どこまで探索すべきかの境界線（Scope）が曖昧なため、無意味なページを行き来し、数時間で数万円〜十数万円分のAPIクレジットを溶かす。
* **副作用による環境破壊:** ログアウトボタンを連打してセッションを切断する、DB内のマスタデータを不正に削除・更新してテスト環境を壊す、通知メールを外部顧客へ誤送信する、といった暴走リスク。

外部から闇雲に叩くだけのブラックボックスアプローチでは、ノイズの海に沈むか、暴走事故を起こすかの二者択一になってしまうのです。

## 1.3 守る側の特権「ホワイトボックス」の優位性

ここで立ち止まって考える必要があります。

攻撃者がブラックボックスで探索せざるを得ないのは、彼らがシステムの「外側」にいるからです。コードも読めず、DBも見えず、エラーログも覗けないからこそ、LLMを使って推論と試行錯誤を繰り返すしかありません。

しかし、**私たちはシステムの「内側」にいます。**

守る側には、攻撃者が喉から手が出るほど欲しい情報と権限が、最初からすべて手元に揃っています。この圧倒的な非対称アドバンテージをエージェントに授けることこそが、本書の提唱する**「ホワイトボックス型自律診断ハーネス」**の基本思想です。

```text
攻撃側（ブラックボックス）:
  × ソースコードは見えない（リバースエンジニアリング・推測）
  × 認証情報は手探り（ログイン突破が必要）
  × DBの状態変化は見えない（レスポンスの僅かな違いから推測）
  × アタックサーフェスはURLを片っ端からクロールして特定

守る側（ホワイトボックス）の特権:
  ◎ ソースコードを直接読ませられる（ルーティング・認可ロジック直読）
  ◎ 認証セッション・テスト用JWT・ロールを自由にプロビジョニング可能
  ◎ テストDBを直接クエリしてデータ改ざんの有無を機械判定（Oracle）
  ◎ OpenAPI定義やTrivyスキャン結果から「怪しい箇所」をピンポイント指定
```

### 1. コード直読による「アタックサーフェス特定のショートカット」
外部からクローラーを回して隠しパラメータを探す必要はありません。エージェントにルーティング定義（`routes/web.php` や `express.Router()`）やコントローラを読ませれば、どのエンドポイントが存在し、どんなパラメータを受け取り、どこに認可チェック（ミドルウェア）が挟まっているかは数秒で把握できます。

探索の労力をゼロにして、いきなり「怪しいロジックの検証」からスタートできるのです。

### 2. 状態（セッション・テストデータ）の自在なコントロール
BOLAを診断したいなら、ハーネス側で「テナントAの管理者トークン」と「テナントBの一般ユーザートークン」をあらかじめ用意し、エージェントのコンテキストに注入すれば済みます。認証の壁を乗り越えるための無駄な足掻きを一切排除し、本質的な権限昇格ロジックの検証に集中させることができます。

### 3. テストDB直接参照による「完全なオラクル（判定機）」
ブラックボックス診断の最大の泣き所は、「本当に攻撃が成功したか」の判定が曖昧な点でした。

しかしホワイトボックス環境であれば、エージェントがエクスプロイトリクエストを送った直後に、**テストDBの中身をSQLで直接確認**できます。「別テナントのレコードが更新されているか」「パスワードハッシュが上書きされたか」をDBから直接検出すれば、誤検知率は原理的にゼロになります。Shannonが掲げる「No exploit, no report（実証なき報告はノイズ）」を、極めて高い確度で達成できるのです。

### 4. 隔離された使い捨て（Ephemeral）環境
「事故が怖い」という問題も、ホワイトボックスなら解決できます。外部ネットワークから切り離されたDockerコンテナ内にターゲットアプリとDBを立ち上げ、診断が終わればコンテナごと破棄（Ephemeral）する設計にすれば、本番環境への誤爆やデータ破壊の心配は一切不要になります。

## 本書で作るもの・目指すゴール

本書で読者の皆さんと一緒に作っていくのは、世の中に転がっているような「汎用ペンテストツールをラッパーしたスクリプト」ではありません。

自社の開発サイクル・CI/CDに組み込み、開発者がPR（プルリクエスト）を出した瞬間、背後で静かに動き出して**「コードを読み、画面を歩き、認可の穴を自律実証し、再現コード（curl）付きでレポートを返す」自社専用のセキュリティハーネス**です。

```text
[開発者のPR作成]
       │
       ▼
[自社診断ハーネス起動 (Temporal)]
       │
       ├─ Step 1: 変更差分・ルーティング・事前スキャン結果を読み込み
       ├─ Step 2: Playwrightで画面を探索し、コードとUIをマッピング
       ├─ Step 3: 最小限のツール（rg, curl）で攻撃仮説を自律検証
       ├─ Step 4: テストDBを直接参照してPoC成否を判定（オラクル）
       │
       ▼
[開発者へ1発で直せる再現レポートを通知]
```

次章では、このハーネスを設計するにあたって欠かせない2つの偉大な先行事例——**Strix** と **Shannon** のアーキテクチャを解剖し、彼らの思想から何を学び、何を削ぎ落とすべきかを明らかにしていきます。
