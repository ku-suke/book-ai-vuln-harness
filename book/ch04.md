# 第4章：ハーネスの全体構造と安全な隔離基盤（auditkitの設計）

ここまでの章で、「なぜホワイトボックスでやるのか」「先人から何を学ぶか」「どのモデルをどう動かすか」という前提が揃いました。

いよいよ本章から、自社専用の脆弱性診断ハーネスの具体的な設計と実装に入っていきます。本書では、僕が実際に開発を進めているベース実装 **`auditkit`** の構造を元に、各コンポーネントをどう組み立てていくかを順を追って解説します。

ハーネスを組む上で一番大切にしたいのは、**「現場で安心して放っておけること（安定性）」と「絶対に外部に迷惑をかけないこと（安全性）」の両立**です。この2つをどうやって仕組みとして担保するのかを見ていきましょう。

---

## 4.1 システムアーキテクチャ

「AIに診断させるスクリプト」と聞くと、Pythonで数十行のコードを書いて、プロンプトをループで回すだけのものを想像するかもしれません。

趣味の実験ならそれでも動きますが、CI/CDに組み込んで開発フローの裏で日常的に回すとなると、すぐに破綻します。診断タスクは平気で数分から数十分、規模によっては1時間以上かかりますし、その間にLLMのレートリミットに引っかかったり、コンテナがメモリ不足で落ちたり、ネットワークが瞬断したりするからです。

そこで `auditkit` では、次のような3層構造を採用しています。

```text
[プルリクエスト / 手動トリガー]
       │
       ▼
┌───────────────────────────────────────────────┐
│ 1. オーケストレーション層 (Temporal)          │
│    └─ 診断フロー全体の状態管理・タイムアウト・リトライ │
└──────────────────────┬────────────────────────┘
                       │ タスクディスパッチ
                       ▼
┌───────────────────────────────────────────────┐
│ 2. エージェント層 (pi.dev)                     │
│    └─ LLMとの推論ループ、ツールの呼び出し制御     │
└──────────────────────┬────────────────────────┘
                       │ コマンド実行 (rg, curl, browser)
                       ▼
┌───────────────────────────────────────────────┐
│ 3. 実行・隔離層 (Worker コンテナ)              │
│    └─ ターゲットアプリと使い捨てDBを閉じ込めた環境   │
└───────────────────────────────────────────────┘
```

### 1. オーケストレーション層：Temporal
Shannonでも採用されている **Temporal** ですが、実際に使ってみると診断ハーネスとの相性が抜群に良いことが分かります。

Temporalは、いわば「途中で落ちても確実に続きから再開できるワークフローエンジン」です。
コード上は普通の関数呼び出しのように書いているだけで、背後で実行状態や変数がすべて永続化されます。たとえば「画面の探索中にLLMがレートリミットで止まった」としても、Temporalが自動で指数バックオフを挟んでリトライしてくれますし、ワーカーのプロセスが急に再起動しても直前のステップから何事もなかったかのように復帰できます。

「長時間かかるタスクを途中で見失わない」ための背骨として、Temporalを中央に据えています。

### 2. エージェント層：pi.dev
実際にLLMと対話しながら「次に何をすべきか」を判断するエージェント基盤には、**pi（pi.dev）** を採用しています。

piは、コーディングエージェントのように「LLMの推論結果を受けて、適切なツール（ripgrep、curl、Playwrightなど）を実行し、その出力をまたLLMに返して次の行動を決めさせる」というReActループをシンプルかつ堅牢に回すための仕組みを提供してくれます。

### 3. 実行・隔離層：Workerコンテナ
実際にコマンドを実行したり、ターゲットのWebサーバーにリクエストを送ったりする処理は、すべてDockerコンテナの中に閉じ込めます。ホストマシンのファイルシステムやネットワークから完全に切り離すことで、不意の事故を防ぎます。

## 4.2 「絶対に事故らせない」サンドボックス境界

自律エージェントをセキュリティ検証で動かすとき、開発者が最も肝を冷やすのは**「意図しない外部サービスへの誤爆」**です。

テスト環境のつもりで動かしていたのに、
* 問い合わせフォームに大量のテストデータを送信して、実在する営業チームのSlackやメールをパンクさせた
* 決済処理の検証中に、外部の決済代行サービス（Stripeなど）のAPIを連打してアカウントを止められた
* アプリのログアウト処理を叩いたつもりが、外部のSaaS連携を解除しに行ってしまった

といった事故は、笑い話ではなく普通に起こり得ます。エージェントは悪気があってやっているのではなく、「与えられた目標（脆弱性の探索）を達成するために、画面にあるボタンやAPIを手当たり次第に試しただけ」だからです。

だからこそ、プロンプトで「外部にアクセスしないでね」とお願いするのではなく、**インフラの物理的な境界（サンドボックス）で絶対に外に出られないように封じる**必要があります。

```text
安全なサンドボックス境界のイメージ:

┌── Docker 内部ネットワーク (隔離空間) ───────────────┐
│                                                      │
│  [Workerコンテナ] ──(HTTP)──> [ターゲットWebアプリ]   │
│   (pi + エージェント)             │                   │
│                                   └──(SQL)──> [テストDB]
│                                                      │
└──────────────────────┬───────────────────────────────┘
                       │ × 外部への通信は全遮断
                       ▼
             [インターネット / 外部SaaS]
             (Stripe, SendGrid, 社内Slackなど)
```

具体的には、以下の3つの防護壁を張ります。

### 1. 外部ネットワークの物理遮断（Internal Network）
Dockerのネットワーク設定で、ターゲットアプリとDBが動くネットワークを外部インターネットから切り離します（`internal: true`）。エージェントがどんなに外部ドメインへリクエストを投げようとしても、名前解決すらできずに即座に失敗するようにしておきます。

### 2. 外部APIや通知のモック化
もしアプリの起動に外部SaaSとの疎通が必要な場合は、本物のAPIキーを入れるのではなく、WireMockやローカルのスタブサーバーに向けておきます。メール送信も、MailHogやMailpitのような「送ったつもりになってブラウザで確認できるだけのダミーSMTPサーバー」に差し替えます。

### 3. 診断用トークンのスコープ限定
エージェントに渡すログインセッションやAPIトークンは、診断対象の組織・テナントだけに絞り込み、他社の本番データや共通マスタを触れないロールに限定しておきます。

## 4.3 安全なテスト環境のプロビジョニング

「安全に思いっきり殴る」ためのもう1つの要が、**使い捨て（Ephemeral）のデータベース環境**です。

認可の不備やビジネスロジックの穴を検証するとき、エージェントはデータを書き換えたり消したりするリクエストを平気で投げてきます。もし共有のステージングDBをそのまま使っていたら、他の開発者が作ったテストデータが消し飛んで阿鼻叫喚になりますよね。

そのため、診断を実行するたびに「その実行のためだけの使い捨て環境」を自動で用意（プロビジョニング）します。

```text
使い捨て環境のライフサイクル:

[診断タスク開始]
       │
       ▼
[Docker Compose でクリーンなDBを立ち上げ]
       │
       ▼
[マイグレーション実行 ＆ テスト用のシードデータを投入]
       │ (ユーザーA、ユーザーB、初期データなどをセット)
       ▼
[エージェントによる診断実行 (心置きなく破壊してOK)]
       │
       ▼
[診断完了後、ボリュームごと即座に破棄 (down -v)]
```

### シードデータの自動投入で「文脈」を渡す
第1章でお話しした通り、ホワイトボックスの最大の強みは「ログインセッションやテストデータを最初から用意できること」です。

データベースを立ち上げた直後、あらかじめ用意したシードスクリプトを実行して、次のようなテストデータを流し込みます。

* **テナントAの管理者:** `admin_a`（ID: 1）
* **テナントAの一般ユーザー:** `user_a`（ID: 2）
* **テナントBの一般ユーザー:** `user_b`（ID: 3）
* **テナントAが所有するプロジェクトや書類データ**

そして、これらのユーザーのログイン済みJWTやセッションCookieをあらかじめ生成し、エージェントのコンテキストに「はい、これが診断用のユーザー情報だよ」と渡してあげます。

こうすることで、エージェントはログイン画面のバリデーションやCAPTCHAに悩まされることなく、最初から「ユーザーBのトークンを使って、テナントAの書類ID（123）を更新できるか？」という本質的な検証に突入できるわけです。

## まとめ

本章では、ハーネスを支える実行基盤のアーキテクチャと安全設計について見てきました。

* **3層構造:** Temporal（オーケストレーション）＋ pi.dev（エージェント）＋ Workerコンテナ（隔離実行）
* **サンドボックス境界:** 外部通信の物理遮断とモック化により、外部SaaSや社内への誤爆をゼロにする
* **使い捨て環境:** 診断ごとにDockerでDBを立ち上げ、シードデータを注入して、終わったら丸ごと消す

足場がしっかりと固まったところで、次章からは**「どうやって診断を効率化するか」**という探索フローの設計に入ります。

闇雲に全探索させるのではなく、Trivyによる事前スキャン結果を「シード情報」としてエージェントに渡すことで、怪しい箇所をピンポイントに攻めさせるテクニックを解説します。
