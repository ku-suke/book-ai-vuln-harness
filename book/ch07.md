# 第7章：実践 —— 自律検証フローの組み立て

前章で、画面を歩き（Playwright）、通信を拾い、コントローラのコード（ripgrep）まで辿り着く方法が分かりました。

いよいよここから、エージェントが実際に細工したリクエストを組み立てて脆弱性を確かめる**「実証（Exploitation）のループ」**を組み立てていきます。

本章では、エージェントが推論を回す基本サイクルを整理した上で、現場で特に狙われやすく、かつ静的解析ツールでは見つけにくい3つの代表的なシナリオ（BOLA、状態遷移、既知CVEの到達性）を題材に、具体的な検証フローを見ていきましょう。

---

## 7.1 検証ループの基本原則

エージェントに脆弱性を検証させるとき、適当に指示を出すと「とりあえず怪しい文字列を片っ端から投げてみる」という大味な動きになりがちです。

そうではなく、熟練のエンジニアが頭の中でやっているような**「4つのステップ」**を意識してループを回させます。

```text
エージェントの基本検証ループ:

1. [Contextの理解]
   └─ 画面の入力項目、飛んだHTTPリクエスト、バックエンドのコードを読む
         │
         ▼
2. [シナリオの仮説立案]
   └─ 「コードのこのチェックが抜けているから、こう叩けば抜けるのでは？」と考える
         │
         ▼
3. [実証リクエストの実行]
   └─ パラメータやヘッダを細工し、curlなどで実際にリクエストを叩く
         │
         ▼
4. [一次判定とフィードバック]
   └─ レスポンスを読み、「仮説通りに動いたか」「WAFや型チェックで弾かれたか」を分析
         │ (ダメなら仮説を修正して3へ戻る / 成功なら次章のオラクルへ)
```

この「仮説を立ててから叩く」というプロセスを挟むことで、無駄撃ちリクエストを劇的に減らすことができます。

## 7.2 実践1：認可制御不備（BOLA / IDOR）の検証

Webアプリの脆弱性で圧倒的に多く、しかも静的スキャナが最も見逃しやすいのが**BOLA（Broken Object Level Authorization / IDOR）**です。

「他人のリソースIDを指定したときに、権限チェックをすり抜けてアクセスや更新ができてしまう」という問題ですね。

### 検証シナリオ
* **状況:** プロジェクト管理アプリ。
* **テナントAのユーザーA:** プロジェクトID `101`（機密プロジェクト）を所有している。
* **テナントBのユーザーB:** まったく無関係な別企業の一般ユーザー。
* **目標:** ユーザーBのトークンを使って、プロジェクト `101` の名前を勝手に書き換えられるか？

### エージェントの自律思考とアクション

エージェントには、第4章で用意したテストユーザー情報（ユーザーAとユーザーBのトークン）をあらかじめ渡しておきます。

```bash
# 1. 正常系: ユーザーA本人がプロジェクト101を更新するリクエストを確認
$ curl -X PATCH https://target.local/api/projects/101 \
  -H "Authorization: Bearer <TOKEN_USER_A>" \
  -H "Content-Type: application/json" \
  -d '{"name": "A社の新規事業計画"}'
# => 200 OK で正常に更新される
```

次に、エージェントは `ProjectController.php` のコードを読みに行きます。

```php
public function update(Request $request, $id)
{
    $project = Project::find($id);
    
    // プロジェクト名は更新しているが、
    // $project->owner_id == Auth::id() のようなチェックが見当たらない！
    $project->update([
        'name' => $request->input('name'),
    ]);
    
    return response()->json($project);
}
```

コードを読んだエージェントは、「あ、権限のチェックがないな」と確信を持ちます。そして、トークンを**ユーザーBのものに差し替えた実証リクエスト**を組み立てて実行します。

```bash
# 2. 攻撃試行: 他人（ユーザーB）のトークンでプロジェクト101の更新を試みる
$ curl -X PATCH https://target.local/api/projects/101 \
  -H "Authorization: Bearer <TOKEN_USER_B>" \
  -H "Content-Type: application/json" \
  -d '{"name": "HACKED_BY_USER_B"}'
```

もしここで `403 Forbidden` が返ってくれば「別のミドルウェア等で守られていた」と判断して撤退します。しかし、もし `200 OK` が返ってきてしまったら……認可不備（BOLA）の成立です。

## 7.3 実践2：状態遷移・ビジネスロジックの抜け穴検証

2つ目のシナリオは、複数画面にまたがる手続きや、ステートマシン（状態遷移）のスキップです。

ECサイトや申込フォームなどでよく見られる、「画面上はボタンを押せないように非活性（disabled）にしてあるけれど、APIを直接叩いたら順番を飛ばせてしまった」という類の穴ですね。

### 検証シナリオ
* **状況:** ドキュメントの承認ワークフロー。
* **正規のフロー:** `下書き（Draft）` → `承認申請（Pending）` → `承認者による承認（Approved）` → `公開（Published）`。
* **目標:** 一般ユーザーが、申請や承認のステップを飛ばして、いきなり `Published` に変更できるか？

### エージェントの自律思考とアクション

エージェントはまず、ドキュメントの更新処理に関するモデルやコントローラを検索します。

```php
public function updateStatus(Request $request, $id)
{
    $doc = Document::find($id);
    $newStatus = $request->input('status');
    
    // 画面上はドロップダウンで「Pending」しか選べないように制御されているが、
    // API側では受け取った文字列をそのまま保存しているだけ……？
    $doc->status = $newStatus;
    $doc->save();
    
    return response()->json($doc);
}
```

コードから「バックエンド側で現在のステータスをチェックするガード条件（FSM: 有限オートマトン）がない」ことを見抜いたエージェントは、通常の手順をスキップするリクエストを投げます。

```bash
# 下書き（Draft）状態の書類に対し、いきなり status=published を送りつける
$ curl -X POST https://target.local/api/documents/55/status \
  -H "Authorization: Bearer <TOKEN_USER_A>" \
  -H "Content-Type: application/json" \
  -d '{"status": "published"}'
```

画面だけを見ているスキャナでは絶対に思いつかない、「コードのステート定義を読んだからこそできる順序飛ばし」の検証です。

## 7.4 実践3：既知CVE（ライブラリ脆弱性）の到達可能性（Reachability）検証

3つ目は、第5章でお話しした「Trivy等で見つかった既知の脆弱性（CVE）が、本当に自社アプリから悪用できるのか？」の検証です。

### 検証シナリオ
* **状況:** 画像をアップロードするとリサイズしてくれる機能がある。
* **Trivyの警告:** 使っている画像処理ライブラリに、「SVGファイル内の細工されたXMLをパースするとXXE（XML外部実体参照）が起きる」というCVEが出ている。
* **目標:** ユーザーがアップロードした画像が、本当にその脆弱な関数に渡っているか？

### エージェントの自律思考とアクション

エージェントは `ripgrep` でその画像処理ライブラリが呼び出されている箇所を追跡します。

1. コントローラ `AvatarController.php` でファイルを受け取っている。
2. 拡張子のチェックを見たら、`jpg, png, svg` が許可されている。
3. そのまま脆弱なバージョンの画像ライブラリのパース関数にファイルパスが渡されている。

「実行パス（ルート）が繋がっている」ことを確信したエージェントは、無害な検証用Payload（外部へリクエストを飛ばすだけの安全なPoC）を含んだSVGファイルを組み立ててアップロードしてみます。

```bash
# 外部への到達確認用Payloadを含んだSVGを送信してみる
$ curl -X POST https://target.local/api/user/avatar \
  -H "Authorization: Bearer <TOKEN_USER_A>" \
  -F "avatar=@poc.svg"
```

ライブラリのバージョンが古いだけでなく、「実際に外からリクエストが届いて脆弱な処理が走る」ところまで実証できた瞬間です。

## まとめ

本章では、エージェントが自律的に脆弱性を検証する3つの実践パターンを見てきました。

* **BOLAの検証:** ユーザーAとBのトークンを使い分け、認可チェック漏れを突く
* **状態遷移の検証:** コードのステート定義を読み、API直接叩きによる順序スキップを突く
* **到達可能性の検証:** 既知CVEのライブラリが、外部からの入力値と実際に繋がっているかを確かめる

どのパターンでも共通しているのは、**「ソースコードが見えているからこそ、的外れな総当たりをせずに、急所を突くリクエストを組み立てられる」**という点です。

しかし、リクエストを投げたあと、もう1つ重要な仕事が残っています。  
それは**「本当に攻撃が刺さったのかをどうやって判定するか」**です。

「画面にはエラーが出ているけれど、実は裏でDBが書き換わっていた」  
「ステータス200が返ってきたけれど、実は何も起きていなかった」

こうした判定のズレをなくすための仕掛けが、次章のテーマである**「判定エンジン（オラクル）の設計とPoCレポートの自動化」**です。
