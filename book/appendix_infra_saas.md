# 付録（Appendix）：インフラ・ミドルウェア・SaaS設定チェックの現実解

本書の本編では、最も開発者の文脈理解が求められ、既存ツールでの自動化が難しかった「Webアプリケーション層（BOLAやビジネスロジック）」の自律診断に焦点を当ててきました。

しかし、実際のシステムを守るためには、アプリケーションコードの背後にある**「インフラ・ミドルウェア」**や、周辺を取り囲む**「SaaS・クラウドの設定（SSPM / CSPM）」**の安全性も無視できません。

初期の壁打ちでも触れた通り、これらをアプリケーション診断と同じノリで「ネットワークが全部繋がった状態でAIに丸ごと殴らせる」と、ほぼ確実に事故を起こします。

本付録では、インフラ層とSaaS設定チェックを安全かつ効率的に自動化するための「現実的なアプローチとレイヤー分割」について整理します。

---

## 1. 診断対象の3つのレイヤー分割

セキュリティ検証を行う際は、以下の3つのレイヤーを明確に切り離して考える必要があります。

```text
3つの診断レイヤーと推奨アプローチ:

┌────────────────────────────────────────────────────────┐
│ 1. アプリケーション層 (本書のメイン)                   │
│    └─ BOLA, 状態遷移, ビジネスロジック                 │
│    └─ アプローチ: 使い捨て環境 + AIハーネス (auditkit)  │
├────────────────────────────────────────────────────────┤
│ 2. インフラ・ミドルウェア層                             │
│    └─ 公開ポート, コンテナイメージ, OS/ミドル設定, IaC  │
│    └─ アプローチ: 静的スキャン (Trivy, Checkov) + 軽量CLI │
├────────────────────────────────────────────────────────┤
│ 3. クラウド・SaaS設定層                                │
│    └─ IAM権限, GitHub/Slack設定, 設定ドリフト          │
│    └─ アプローチ: Read-Onlyトークン + 設定監査          │
└────────────────────────────────────────────────────────┘
```

なぜ分けるべきなのかというと、**「必要な権限」と「事故が起きたときの影響範囲」が全く異なるから**です。

## 2. インフラ・ミドルウェア層の現実解

### ライブ環境を殴る前に、コード（IaC）で機械的に叩き落とす

インフラの診断というと、昔ながらの「外側からNmapでポートスキャンをかけ、脆弱性スキャナでミドルウェアを叩く」アプローチを思い浮かべるかもしれません。

しかし現代のクラウド開発において、稼働中のコンテナやサーバーに対してAIにポートスキャンを走らせるのは、時間もコストもかかる割に得られるものが少ないです。

現代のインフラ診断の鉄則は、**「IaC（Infrastructure as Code）とコンテナイメージの段階で、機械的にスキャンし尽くす」**ことです。

#### 1. コンテナイメージ・OSパッケージスキャン
Dockerfileやビルド済みコンテナイメージは、第5章でも触れた **Trivy** で一撃でスキャンできます。

```bash
# ビルドしたDockerイメージ内のOS脆弱性をスキャン
$ trivy image my-app:latest
```

ベースイメージが古かったり、脆弱なパッケージが紛れ込んでいれば、デプロイ前のCIの段階で即座に検知して落とせます。

#### 2. IaC（Terraform / CloudFormation / k8sマニフェスト）の静的解析
セキュリティグループの全開放（`0.0.0.0/0`）や、S3バケットのパブリック公開、暗号化の無効化といった設定ミスは、インフラを実際にプロビジョニングする前の**コードの段階**で発見できます。

* **Checkov** や **tfsec**, **Trivy (config scan)** などのツールを使えば、TerraformファイルやKubernetesのマニフェストを走査して、CISベンチマーク等のセキュリティ基準に反する設定を数秒で弾いてくれます。

```bash
# Terraformのコードを静的スキャンする
$ checkov -d ./terraform
# または
$ trivy config ./terraform
```

ここをCIで自動化しておくだけで、「うっかりSSHポート（22）を世界中に公開してしまった」といった事故は100%防げます。

### それでもライブ環境で確認したい場合の割り切り
「ステージング環境で本当に意図しないポートが開いていないか」「WAFの設定が意図通り効いているか」といったライブ検証を行いたい場合は、アプリケーションの診断ハーネスとは切り離し、**Nuclei** や **httpx** といった軽量で高速なCLIツールを使って、ピンポイントで疎通チェックを行うジョブを組むのが安全です。

## 3. クラウド・SaaS設定（SSPM / CSPM）の現実解

近年、重大なインシデントの引き金になりやすいのが、**クラウドやSaaSの設定ミス（過剰な権限、野良トークンの放置、設定ドリフト）**です。

* AWS IAMで `AdministratorAccess` が付いたアクセスキーが開発者個人のPCに落ちている
* GitHubリポジトリの設定で、誰でもプライベートリポジトリをフォークできるようになっている
* Google WorkspaceやSlackで、退職者のアカウントや外部ゲストに過剰な権限が残っている

### エージェントに書き込み権限を絶対に渡してはいけない
こうしたSaaS設定をAIで監査しようとするとき、**最も危険なのはエージェントに「更新（Write）」の権限を渡すこと**です。

もしエージェントが「このIAMポリシーは権限が広すぎるから削っておこう」と良かれと思って変更した結果、全社の本番アクセスが遮断されたり、認証設定が吹き飛んで全員がログインできなくなったりしたら目も当てられません。

### Read-Only（閲覧専用）トークンによる設定監査
SaaSやクラウド設定のチェックは、**「Read-Onlyトークンで設定JSONを引っ張ってきて、AIに突合・分析させる」**という形に徹底して絞り込みます。

```text
SaaS設定監査の安全なフロー:

[Read-Only APIトークン]
       │ (AWS IAM, GitHub API, Slack API など)
       ▼
[設定情報のダンプ (JSON)]
  ・IAMロールとポリシー一覧
  ・リポジトリの保護ブランチ・権限設定
       │
       ▼
[監査エージェント (推論のみ・副作用ゼロ)]
  「このポリシーはワイルドカード(*)が使われていて広すぎる」
  「MFAが必須になっていない管理ユーザーがいる」
       │
       ▼
[開発者・セキュリティ担当者へ修正ガイドをレポート]
```

エージェント自身には設定を変更する権限を一切持たせず、「設定ファイルやAPIから吸い出した現状の構成（JSON）」を渡して、「社内のセキュリティガイドラインと照らし合わせて、過剰な権限や怪しい設定がないかレビューしてくれ」と依頼するだけです。

これなら、本番のインフラやSaaSに一切の副作用を与えることなく、AIの文脈理解力を活かして設定の不備をあぶり出すことができます。

## まとめ：適材適所で守りを固める

AIエージェントによる脆弱性診断は非常に強力ですが、何でもかんでも1つのエージェントにやらせようとすると、事故のリスクとコストが跳ね上がります。

* **Webアプリのロジック・認可:** ホワイトボックス型AI診断ハーネス（本書のメイン）で実証する
* **インフラ・コンテナ・ミドル:** IaCスキャンやコンテナスキャン（Trivy, Checkov等）で、ビルド前のコード段階で機械的に防ぐ
* **クラウド・SaaS設定:** Read-Onlyトークンで設定を吸い出し、AIに読み込ませて権限過多をレビューする

「どこまでを静的なツールで落とし、どこからをAIに任せるか」「どこに安全な境界を引くか」。このレイヤーごとの適切な割り切りこそが、現場で事故を起こさずにセキュリティを自動化するための最大のポイントです。
