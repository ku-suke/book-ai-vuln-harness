# 第6章：人間診断員に学ぶ「ウォークスルー」とUI/コードマッピング

外部のセキュリティ診断会社にWebアプリの脆弱性診断をお願いしたことがある方なら、診断が始まる前に「ウォークスルー（事前ヒアリングや画面のデモ）」を行うプロセスを経験したことがあるかもしれません。

診断員は、いきなりツールを起動して攻撃を仕掛けるのではなく、まずブラウザで画面をひと通りポチポチ触りながら、「このアプリにはどんな画面があって、管理者と一般ユーザーで何が違って、裏でどんなAPIが飛んでいるのか」を把握していきます。人間は画面を触ることで、頭の中に「アプリの全体像」という大切な文脈を組み立てているわけです。

ホワイトボックスで自社ハーネスを作る際、この**「人間の診断員がやっている画面ウォークスルー」をAIエージェントにやらせる**と、診断の精度が跳ね上がります。

本章では、Playwrightを使って画面を歩き、裏で飛んだ通信を手がかりに、エージェント自身がソースコードへ辿り着く「UIとコードのマッピング」の仕組みを解説します。

---

## 6.1 診断員の初期アプローチをモデル化する

ブラックボックスのスキャナがなぜBOLA（認可不備）やビジネスロジックの穴を見つけられないかというと、「画面の操作」と「裏側のプログラム」の繋がりが全く見えていないからです。

外部から見ると、`POST /api/projects/123/invite` というリクエストが1つ飛んでいるだけにしか見えません。しかし人間の診断員は、
* 「いま画面上で『プロジェクト設定』を開いて、『メンバー招待』ボタンを押した」
* 「フォームにはメールアドレスとロール（権限）の選択肢があった」
* 「裏ではおそらくProjectControllerの招待処理が動いていて、DBの中間テーブルにレコードをインサートしているはずだ」

という一連のストーリーとして理解しています。

```text
人間の診断員の頭の中:
[ブラウザ画面の操作] 
       │ (画面上のボタンや入力フォーム)
       ▼
[飛んだHTTPリクエスト] 
       │ (URLパス, メソッド, JSONボディ)
       ▼
[裏側で動いているバックエンドコード]
       │ (ルーティング, コントローラ, 認可ミドルウェア)
       ▼
「あ、これ、別のユーザーのプロジェクトIDを指定したらどうなるんだろう？」(仮説)
```

この「画面操作 ↔ 通信 ↔ ソースコード」の3点を繋ぎ合わせる作業を、エージェントの診断フローの第一歩として組み込んでいきます。

---

## 6.2 Playwrightを用いたUI探索と通信のキャプチャ

まず行うのが、**Playwrightを使った自動巡回（探索）**です。

テスト環境が立ち上がったら、エージェントにPlaywrightのブラウザを操作させ、あらかじめ用意しておいたテストユーザー（第4章のシードユーザー）でログインさせます。

### 通信をすべてインターセプト（傍受）する
ブラウザを歩かせる際、ただ画面を開くだけでは意味がありません。Playwrightのネットワーク監視機能を使って、**「ブラウザが裏でやり取りしたすべてのHTTPリクエストとレスポンス」を記録**します。

```python
# Playwrightで通信をキャプチャするイメージ (疑似コード)
captured_traffic = []

def handle_request(request):
    # 静的ファイル（css, js, 画像など）は除外し、APIや画面遷移だけを記録
    if request.resource_type in ["fetch", "xhr", "document"]:
        captured_traffic.append({
            "url": request.url,
            "method": request.method,
            "headers": request.headers,
            "post_data": request.post_data
        })

page.on("request", handle_request)
```

エージェントが画面上のリンクをクリックしたり、ダミーの値をフォームに入力して送信したりするたびに、裏側で叩かれたAPIのURLやパラメータがどんどんログとして蓄積されていきます。

これで、**「どの画面を触ると、どんなHTTPリクエストが飛ぶのか」**という通信ログのリストが手に入りました。

> **コラム：隔離環境で「そもそも動いていない画面」を洗い出す効果**  
> 実はこのウォークスルー、脆弱性を探すためだけでなく、**「隔離されたテスト環境で、そもそも正常に動かない画面をあらかじめ洗い出す」**という実用的な副産物があります。  
> 人間の診断会社にお願いしたときにもよくあるのですが、「テスト中に画面が500エラーで落ちたけれど、これって攻撃が刺さって落ちたのか、単にテスト環境のDBに初期データが入っていなかったり、外部連携が繋がっていなかったりするだけの『単なる不具合』なのか判断がつかない」というケースが結構あります。  
> 本格的な攻撃検証を始める前に、エージェントにPlaywrightで通常利用のウォークスルーを一通り流させることで、「正常系すら動いていない壊れた画面」を事前にリストアップして除外・修正できます。これにより、本番の診断フェーズで「環境の不備によるニセのアラート」に振り回されるのを防ぐことができるわけです。

## 6.3 エージェント自律探索によるコードマッピング

さて、ここからがホワイトボックスならではの面白いところです。手に入った通信ログ（エンドポイント）から、**「対応するバックエンドのコード（ControllerやRouter）」を特定**します。

### 専用パーサーを作り込むと沼にハマる
ここで真面目なエンジニアほど、「URLのパスからControllerのファイル名を特定するASTパーサーを書こう！」と頑張ってしまいがちです。

ですが、それはおすすめしません。世の中にはLaravel、Rails、Express、FastAPI、Next.js、Djangoなど無数のフレームワークがあり、ルーティングの書き方もアノテーションだったり設定ファイルだったりとバラバラです。フレームワークごとに専用パーサーを作っていたら、それだけで本業が終わってしまいますし、本書の本筋からもズレてしまいます。

### 「エージェントはやたらrgを使いがち」をそのまま活かす
そこで、**「エージェント自身に `ripgrep`（rg）で自律的に探させる」**という割り切りを採用します。

ClaudeやGPTなどのコーディングエージェントを普段使っている方なら共感していただけると思いますが、彼らはファイルを探すとき、やたらと `ripgrep` を使いこなしますよね。あの習性をそのまま活かせばいいのです。

エージェントにキャプチャしたURLパスを渡し、こう指示します。

> **エージェントへのプロンプト例:**  
> ブラウザ操作により、次のAPIリクエストが確認されました:  
> `POST /api/v1/projects/123/members`  
> 
> 手元の `ripgrep` コマンドを使ってリポジトリ内を検索し、このリクエストを処理しているルーティング定義およびコントローラのソースコードファイルを特定してください。特定したら、そのファイルの中身を読んで処理内容を理解してください。

エージェントはこれを受けて、自発的にコマンドを叩き始めます。

```bash
# エージェントが自律的に実行するコマンドの例
$ rg "projects/.*/members" -g "*.ts" -g "*.php" -g "*.py"
routes/api.php: Route::post('/projects/{project}/members', [ProjectMemberController::class, 'store']);

$ rg "class ProjectMemberController"
app/Http/Controllers/ProjectMemberController.php: class ProjectMemberController extends Controller
```

ルーティング定義が見つかれば、あとはそのコントローラの `store` メソッドを読みにいくだけです。専用のパーサーなど1行も書かなくても、エージェントは数秒で目的のファイルに辿り着いてくれます。

### コードを読んで「認可の穴」にアタリをつける

コントローラのコードを開いたエージェントは、人間と同じように処理の流れを読み解きます。

```php
// 見つかったコントローラの例
public function store(Request $request, $projectId)
{
    // プロジェクトを取得
    $project = Project::find($projectId);
    
    // 【注目】ここで「リクエストを送ってきたユーザーが、このプロジェクトの管理者か？」の
    // 認可チェック（Policyやauthorize）が抜けている……！？
    
    $project->members()->create([
        'user_id' => $request->input('user_id'),
        'role'    => $request->input('role'),
    ]);
    
    return response()->json(['status' => 'success']);
}
```

コードを読んだエージェントは、ここで初めて「仮説」を立てることができます。

> **エージェントの思考ログ:**  
> 「`ProjectMemberController@store` を確認した。プロジェクトの取得時にIDで直接引いているが、操作ユーザーがそのプロジェクトのオーナーであるかどうかの認可チェックが見当たらない。  
> ユーザーBの認証トークンを使って、ユーザーAが所有する `projectId=123` に対するメンバー追加APIを叩けば、認可をバイパスして勝手にメンバーを追加できる可能性がある（BOLA/IDOR）。」

画面操作からスタートし、通信を拾い、コードを読んで、攻撃の仮説を立てる。これで、人間診断員の思考プロセスと全く同じ足場が完成しました。

## まとめ

本章では、人間診断員のアプローチをエージェントに落とし込む「ウォークスルーとコードマッピング」について見てきました。

* **画面と通信のキャプチャ:** Playwrightでブラウザを動かしながら、裏で飛んだAPIリクエストをすべて傍受して記録する
* **専用パーサーを作らない割り切り:** フレームワークごとのルーティング解析器を作り込まず、エージェントに `ripgrep` で自律的に探させる
* **コード読解による仮説立案:** コントローラを直接読むことで、「ここ、認可チェックが抜けているのでは？」という精度の高い攻撃シナリオを組み立てる

画面とコードが結びつき、攻撃の仮説が立ちました。
