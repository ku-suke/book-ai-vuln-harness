# 第9章：自社ハーネスを育てる（CI/CD統合と継続的DevSecOps）

ここまでで、自社専用の脆弱性診断ハーネスのコア機能が一通り揃いました。

しかし、どんなに優れたツールを作っても、ローカルでたまに手動実行するだけでは、いずれ使われなくなって形骸化してしまいます。ツールに魂を吹き込み、本当の「守備力」として機能させるためには、**日々の開発サイクル（CI/CDパイプライン）の中に自然に溶け込ませる**必要があります。

本章では、GitHubのプルリクエスト（PR）をトリガーにして差分だけをサクッと診断する仕組みや、運用で一番気になる「コストと時間のコントロール」、そして自社ハーネスを育て続けていくための心構えについてお話しします。

---

## 9.1 PR（プルリクエスト）単位の軽量差分スキャン

### 毎回フルスキャンを回していては開発が止まる

「PRが出るたびに、アプリ全体の画面とAPIを全探索して診断を回そう！」

これは意気込みとしては素晴らしいのですが、実際にCIで回すと開発チームから確実にクレームが来ます。数十分もCIが終わらず、開発者の手が止まってしまうからです。さらに、毎回大量のトークンを消費するため、API代も馬鹿になりません。

日々のCI/CDで回すなら、**「今回変更されたコードの周辺だけ」を狙い撃ちにする軽量差分スキャン**が鉄則です。

```text
PR単位の軽量差分スキャンの流れ:

[開発者がPRを作成 / コミットをプッシュ]
       │
       ▼
[git diff で変更されたファイルを特定]
  例: `app/Http/Controllers/BillingController.php`
       │
       ▼
[エージェントへのスコープ限定]
  「BillingController.php に紐づくルートと画面だけを対象に診断して」
       │
       ▼
[数分でピンポイントに検証完了 ── 結果をPRコメントに通知]
```

### `git diff` から影響範囲を特定する

やり方はとてもシンプルです。CI（GitHub Actionsなど）の中で `git diff` を叩き、変更されたコントローラやモデルのファイル名を抽出します。

```bash
# mainブランチとの差分から、変更されたControllerファイルをリストアップする
CHANGED_CONTROLLERS=$(git diff --name-only origin/main...HEAD | grep 'Controller')
```

そして、エージェントへの初期プロンプトにこのリストを渡し、「今回はこのファイルに関連するエンドポイントと画面だけを探索してくれ」と制約をかけます。

探索範囲が最初から1〜2個のコントローラに絞られているため、画面のウォークスルーも数ステップで終わり、診断タスク全体が2〜3分程度で完了します。このくらいのスピード感であれば、通常のテストスイートと一緒に回しても開発の邪魔になりません。

## 9.2 運用コスト・安全性のコントロール

自律エージェントをCIで常時稼働させる上で、避けて通れないのが「コスト（トークン代）」と「実行時間」の管理です。

エージェントが途中で迷走して無限ループに陥ったとき、気づいたら1回のPRで数万円分のAPI代が溶けていた……なんてことになったら目も当てられません。安心して放置できるように、ハーネス側で**「絶対に超えられない3重のブレーキ」**を仕込んでおきます。

```text
3重のブレーキ設計:

1. [最大ステップ数 (Max Steps)]
   └─ 例: エージェントの試行回数を「最大15ステップまで」に制限

2. [トークン予算 (Token Budget)]
   └─ 例: 1回の診断で消費できるトークンを「最大50,000トークンまで」に制限

3. [ハードタイムアウト (Temporal)]
   └─ 例: どんなに長くても「5分（300秒）」で強制終了させる
```

### 1. 最大ステップ数の制限（Max Steps）
pi.devなどのエージェント基盤側で、エージェントがツール（rg, curl, Playwright）を呼び出す上限回数を設定します。差分スキャンであれば、15〜20ステップもあれば十分です。上限に達した場合は、「時間切れのため、ここまでの調査結果でレポートを出力する」として安全に終了させます。

### 2. トークン予算（Token Budget）
LLMとやり取りした累積トークン数をカウントし、あらかじめ設定した予算（たとえば1回の実行あたり1ドル相当など）に達したら、そこで推論をストップさせます。

### 3. ハードタイムアウト（Temporal）
第4章で導入したTemporalのワークフロー設定で、全体の実行時間上限（Workflow Execution Timeout）を「5分」などに設定しておきます。もしコンテナがハングアップしたり通信が詰まったりしても、Temporalが強制的にタスクを中断してリソースを解放してくれます。

この3つの安全装置を入れておくことで、「予想外の出費」や「CIパイプラインの目詰まり」を確実に防ぐことができます。

## 9.3 おわりに：自社の「守備力」としてハーネスを育てる

本書では、ARTEXなどの自動攻撃エージェントに対抗するために、防御側の「中身を知っている強み（ホワイトボックス）」を活かした自社ハーネスの設計と実装を見てきました。

セキュリティの世界に「これを入れれば100%安全」という魔法の銀の弾丸はありません。商用の高価なセキュリティSaaSを契約したとしても、自社のビジネスロジックの深い部分や、細かな認可の組み合わせまで完璧に見てくれるわけではないのです。

でも、**自社専用のハーネスなら、自分たちの手でいくらでも育てていくことができます。**

* 「過去にやらかしたバグのパターン」をエージェントのプロンプトに知見として追加する
* 新しく導入した社内フレームワークの書き方に合わせて、探索のヒントを調整する
* 開発チームの好むレポートの形式に合わせて、出力フォーマットを改善する

そうやって日々の開発の中で少しずつ手入れをしていくうちに、そのハーネスは誰にも真似できない**「世界で一番、自分たちのサービスをよく知っている優秀なセキュリティガード」**へと進化していきます。

攻撃側がAIを使って安価に殴ってくる時代だからこそ、守る側の僕らもAIを使いこなし、自分たちの手で誇りを持ってプロダクトを守り抜いていきましょう。

本書が、皆さんのチームの「守備力」を一段引き上げるための一助となれば幸いです。
