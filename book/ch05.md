# 第5章：事前スキャン（Trivy）連携とアタックサーフェスの絞り込み

隔離された安全な実行環境が整ったら、次はエージェントに「どうやって効率よく脆弱性を探させるか」という探索フローの設計に入ります。

ここで絶対にやってはいけないのが、**いきなりAIエージェントに「さあ、このWebアプリの穴を自由に探してくれ」と丸投げすること**です。

何のヒントも与えずに自律探索を始めさせると、エージェントは暗闇の中で手探りするように画面を行き来し、無関係なページや当たり障りのないAPIを叩き続けます。時間もトークン代も湯水のように消えていく上に、「結局何も見つかりませんでした（あるいは見当違いなレポートが1件出ただけ）」という悲しい結末になりがちです。

そこで重要になるのが、**「機械的にできる下調べは既存のツールに任せ、その結果をエージェントへのヒント（シード情報）として渡す」**という役割分担です。

本章では、OSSの脆弱性スキャナである **Trivy** を使って下調べを行い、エージェントの攻撃目標（アタックサーフェス）を賢く絞り込むアプローチを解説します。

---

## 5.1 静的SCA・コンテナスキャンの実施

### 得意なことは得意なツールに任せる

第2章のコラムでも少し触れましたが、依存ライブラリの既知脆弱性（CVE）や、Dockerfileの設定不備といったインフラ寄りのチェックは、わざわざ高価なLLMに考えさせる必要はありません。すでに世の中に優れた静的解析・SCA（Software Composition Analysis）ツールが存在するからです。

その代表格が、オープンソースで広く使われている **Trivy** です。

Trivyを使えば、プロジェクトのディレクトリを指定するだけで、数秒から数十秒で依存関係をスキャンしてくれます。

```bash
# プロジェクトのソースコードと依存関係をスキャンしてJSONで出力する
trivy fs --format json -o trivy-result.json .
```

これだけで、`package-lock.json` や `composer.lock`、`go.sum` などを解析し、「どのライブラリのどのバージョンに、どんなCVEが報告されているか」を一覧にしてくれます。

```json
// Trivy の出力例 (一部抜粋)
{
  "Target": "package-lock.json",
  "Vulnerabilities": [
    {
      "VulnerabilityID": "CVE-2024-XXXXX",
      "PkgName": "sharp",
      "InstalledVersion": "0.32.0",
      "FixedVersion": "0.32.6",
      "Severity": "HIGH",
      "Title": "特定の画像パース時におけるメモリ破壊の脆弱性"
    }
  ]
}
```

人間がこのJSONを見ても、「まあライブラリが古いのは分かったけど、自社コードで実際に悪用できる形（危ない関数）で使ってるんだっけ……？」と調べるのが億劫になって放置されがちですよね。

この「人間がトリアージするのが面倒な部分」こそ、AIエージェントに渡す最高の材料になります。

## 5.2 「シード情報」への変換

### Trivyの結果をエージェントの「探索目標」に変える

Trivyが出力した大量の脆弱性リストを、そのままプロンプトに貼り付けて「直して」と頼んでもうまくいきません。情報量が多すぎてエージェントのコンテキストを圧迫してしまうからです。

そこでハーネス側で、TrivyのJSONから「特に危険度（Severity）が高く、外部からの入力値が絡みそうなもの」をフィルタリングし、**エージェントが検証すべき「優先度付きのタスクキュー（シード情報）」**に変換します。

```text
事前スキャンからシード情報への変換フロー:

[Trivyによる高速スキャン]
       │ (依存関係・Dockerfileをチェック)
       ▼
[生の脆弱性リスト (数百件のCVEが出ることも)]
       │
       ▼ 【フィルタリングと整形】
       │ ・Critical / High のものに絞る
       │ ・自社コードからimport/requireされていそうなパッケージを抽出
       ▼
[エージェントへのシード情報 (優先度キュー)]
  Task 1: ライブラリ「sharp」の画像処理APIに届くルートがあるか？
  Task 2: 旧バージョンのJWTライブラリで署名検証スキップが再現するか？
```

### エージェントへのプロンプティング例

エージェントには、以下のように「具体的な足がかり」を与えて探索をスタートさせます。

> **エージェントへの指示（プロンプト例）:**  
> 事前スキャンの結果、画像処理ライブラリ `sharp (v0.32.0)` に既知の脆弱性 `CVE-2024-XXXXX` が検出されました。  
> 以下の手順で、この脆弱性が自社アプリの外部から実際に突ける状態になっているか（到達可能性）を検証してください。  
> 1. `ripgrep` を使って、リポジトリ内で `sharp` をインポート・利用しているコントローラやサービス層のコードを特定してください。  
> 2. そのコードを呼び出しているWeb画面やAPIエンドポイントが存在するか、ルーティング定義を確認してください。  
> 3. 外部からのファイルアップロードやパラメータ入力が、脆弱性のある処理まで直接届いているかコードを追跡してください。  
> 4. 届いている場合、実際にリクエストを送信して安全に検証できるか仮説を立ててください。

このように足がかり（シード）を与えてあげるだけで、エージェントは無駄なページをうろうろすることなく、**「該当のライブラリを使っているコード」→「それを呼んでいるAPI」**へと一直線に焦点を絞って調査を開始できます。

## 5.3 ツールセットのミニマリズム

シード情報をもとにエージェントを動かす際、もう1つ大切なのが**「エージェントに持たせる道具（Tool）を最小限に絞る」**ということです。

Strixのように、nmap、sqlmap、nikto、gobuster……と大量のツールをエージェントに渡したくなる気持ちは分かります。ツールがたくさんあった方が強そうに見えますからね。

ですが、現場で動かす上では、ツールの増やしすぎは明確にデメリットになります。

### ツールを増やしすぎると何が起きるか？

1. **選択肢が多すぎてエージェントが迷走する:**  
   LLMのツール呼び出し（Tool Calling）は、選択肢が増えるほど「いまどの道具を使うべきか」の判断精度が落ちます。ただコードの中身を検索したいだけなのに、関係ないペンテストツールを呼び出そうとしてエラーになる、といった空振りが増えます。
2. **コンテキストウィンドウを無駄に消費する:**  
   エージェントにツールを持たせるということは、システムプロンプト内に全ツールの定義（引数のスキーマや説明文）を毎ターン流し込むということです。ツールが20個もあれば、それだけで数千トークンが常時消費され、推論コストもレイテンシも悪化します。

### 「rg」「curl」「Playwright」の3種の神器で戦う

`auditkit` では、エージェントに渡すツールを極限まで絞り込んでいます。

| ツール | 役割 | なぜこれで十分なのか |
| :--- | :--- | :--- |
| **`ripgrep` (rg)** | コードの高速検索 | コントローラ名、エンドポイントのパス、利用ライブラリなどを数ミリ秒で探し出せる。エージェントにとって最も馴染みのある検索ツール。 |
| **`curl`** | HTTPリクエスト送信 | パラメータの改ざん、ヘッダの差し替え、JWTの注入など、APIの検証に必要な操作はcurlで100%表現できる。再現コードとしてもそのまま開発者に渡せる。 |
| **`Playwright`** | ブラウザ操作・UI探索 | 画面遷移、入力フォームの入力、ボタンクリックなど、人間と同じようにブラウザを操作して裏で飛ぶ通信をキャプチャする。 |

大掛かりなハッキング専用ツールがなくても、「コードを検索して読み（rg）」「画面を触ってAPIを見つけ（Playwright）」「パラメータをいじってリクエストを叩く（curl）」という3つの基本動作ができれば、Webアプリの脆弱性検証の大半はカバーできます。

道具をシンプルにしておくことで、エージェントの思考もシンプルになり、迷走やエラーの発生率を最小限に抑えられるのです。

## まとめ

本章では、エージェントが無駄足を踏まないための「探索の絞り込み」について見てきました。

* **Trivyとの連携:** 機械的にできるSCAや既知脆弱性スキャンはTrivyに丸投げし、数秒で終わらせる
* **シード情報への変換:** Trivyの検出結果をエージェントへの「優先タスク」に整形して渡すことで、該当コードへのピンポイント調査を可能にする
* **ツールセットの引き算:** `ripgrep`、`curl`、`Playwright` の3つに絞り込むことで、迷走を防ぎ、トークンコストを抑える

さて、エージェントが調べるべき「怪しい箇所」の目星がついたら、次はいよいよ**実際の画面とソースコードをどう結びつけるか**という核心部分に入ります。

次章では、人間の診断員が現場で行う「画面ウォークスルー」の手順をモデル化し、Playwrightで画面を触りながら裏側のコントローラを自律特定させるテクニックを解説します。
